### 按用户要求改的两处

一、PR/issue 条目在标题后缀提交者（`@login`）。拿到什么放什么，拿不到
就整个省略——已删号用户 author 为 null，写"未知"只是噪音。

实现时的坑：合并的 PR 走状态变更路径，而 `StateChange` 原本没 select
`author_login`。只改 `Item` 会让"合并的 PR"成为唯一没作者的一栏。
`store.py` 里有两个构造 `StateChange` 的地方（`upsert_events` 与
`pending_since_last_notify`），都要补，否则首次入库就合并的 PR 与后来
才合并的表现不一致。

commit 事件没有作者数据（`EVENT_LOG_FORMAT` 只取 SHA、日期、标题），
但战报里 commit 只计数不列出，所以没为此扩字段。

二、底部累计从两项补全为四项。数字取自 `summary.csv` 已有的
`pr_created` / `pr_merged` / `issue_created` 三列，不额外发 API 请求——
每日跑的是全量，总量本就每天刷新。

口径保持与 `summary.csv` 一致（按人累加）。注意 `pr_created` 是"窗口内
有贡献的人所创建的 PR"，某人窗口前建的 PR 也计入，故它不等于"窗口内
新建的 PR 数"。保持这个口径是有意的，因为人们要核对的正是那张表。

### 从真实 dry-run 揪出的三处缺陷

这三处都是单元测试测不出来的——测试用的是构造数据，而缺陷只在真实
数据流经完整路径时才显形。

一、首次推送会把历史积压当增量。`is_first_run()` 只挡住第一次运行，
第二次跑时 `_last_notified_run()` 仍返回 0，于是
`pending_since_last_notify()` 交出建库时录入的全部历史。实测：种子运行
录入 1606 条后，卡片把今年一整年的 597 次提交 / 573 个 PR 合并写成
"自上次汇报以来"。

积压只有推送成功才清空，形成死循环。新增 `store.mark_notify_baseline()`
与 `--mark-notified`：首次建库后用一次定基线。该参数不要求 `--notify`，
因为它本就不该发消息。

二、离线路径下底部四项归零。`--no-fetch` 或无当天 API 缓存时
`collect_api_stats` 返回空，`_year_totals` 把三项加成 0，于是底部写
"今年 0 个 PR 合并"，而上方分区正列着 573 个。改为区分不了"真的没有"
与"没取到"时整项省略。

三、范围标注拿错分母。`repos_total` 是组织下全部仓库（67），而全量跑
本就只覆盖其中 34 个，拿 67 当分母会让每次运行都显示成"局部"。改用
新增的 `repos_in_scope`（本次纳入统计范围的仓库数）。

### 日常与全量两种模式

用户要求每天跑一次只维护 `by_repo.csv` 与 `summary.csv`，其余附表只在
全量统计时产出。

```
--daily        → ./output/daily    只写两张总表 + run_meta.json
默认（全量）   → ./output/all      完整产出，与之前的 output_all 一致
```

显式 `--out-dir` 仍可覆盖。两种模式默认写不同目录，日常跑不会覆盖全量
统计的产出。

同时把散落在根目录的结果目录收进 `output/`：

| 原路径 | 新路径 |
|---|---|
| `output_all` | `output/all` |
| `output_gpumd` | `output/gpumd` |
| `output_all_backup_20260731_all_refs` | `output/all_backup_20260731_all_refs` |

这些目录本就不进 git（`.gitignore` 已有 `output/` 与 `output_*/`），
移动零风险。

### 测试污染的修复

二期给 `Config` 加 `events_db` 字段时，`test_integration.mk_cfg` 只重定向了
`cache_dir` 与 `out_dir`，漏了新字段。于是每跑一次集成测试，真实的
`data/events.db` 就被写进 tiny 仓库的假数据一次（实测：runs 表 27 → 36）。

修了三处：`mk_cfg` 显式重定向（根因）、`conftest.py` 加 autouse fixture
兜底（改 `__init__.__defaults__`，不是 `__dataclass_fields__`——后者是
只读 slots 对象且默认值在建类时就烤进了 `__defaults__`）、新增
`test_isolation.py` 两条防线。

以后新增落盘字段，只需在 `conftest._DISK_FIELDS` 加一行。

## 五、已知问题

昨天那三条仍然有效（SECRET、API 限额、事件库不可完全重建），此外新增：

### 新增仓库会把它的全年历史当增量

事件库按 `first_seen_run` 判定增量，所以往 `--repos` 里加一个从没跑过的
仓库时，它今年至今的全部事件都是"本次首次看到"，会一次性涌进战报。

实测：库里只有 deepmd-kit 时加入 dpdata，下一次的战报变成
"125 次提交 · 109 个 PR 合并 · 38 个 PR 新建 · 43 个 issue"，
全是 dpdata 的全年历史，不是当天活动。

处置办法：扩大仓库范围后先跑一次 `--mark-notified` 定基线，再开始
正常推送。

彻底的修法是按仓库分别记基线（新仓库首次出现时自动跳过其历史），
当前未做——每次扩范围手动定一次基线成本很低，而按仓库记基线要改表结构。

### 提交者显示的两个既定取舍

合并的 PR 显示的是创建者而非合并者。谁点的合并按钮是另一个字段
（`mergedBy`），要改得动 GraphQL 查询。当前口径与 CSV 的 `pr_created`
一致，是用户确认过的。

机器人会出现在提交者里（`@njzjz-bot`、`@pre-commit-ci`、
`@copilot-swe-agent` 等）。统计管线有 bot 标注机制，但事件管线只存原始
login。用户确认"拿到什么 id 信息就写什么"，故不过滤。
