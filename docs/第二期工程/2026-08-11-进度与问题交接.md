### 从真实 dry-run 揪出的三处缺陷

这三处都是单元测试测不出来的——测试用的是构造数据，而缺陷只在真实
数据流经完整路径时才显形。

一、首次推送会把历史积压当增量。`is_first_run()` 只挡住第一次运行，
第二次跑时 `_last_notified_run()` 仍返回 0，于是
`pending_since_last_notify()` 交出建库时录入的全部历史。实测：种子运行
录入 1606 条后，卡片把今年一整年的 597 次提交 / 573 个 PR 合并写成
"自上次汇报以来"。

积压只有推送成功才清空，形成死循环。新增 `store.mark_notify_baseline()`
与 `--mark-notified`：首次建库后用一次定基线。该参数不要求 `--notify`，
因为它本就不该发消息。

二、离线路径下底部四项归零。`--no-fetch` 或无当天 API 缓存时
`collect_api_stats` 返回空，`_year_totals` 把三项加成 0，于是底部写
"今年 0 个 PR 合并"，而上方分区正列着 573 个。改为区分不了"真的没有"
与"没取到"时整项省略。

三、范围标注拿错分母。`repos_total` 是组织下全部仓库（67），而全量跑
本就只覆盖其中 34 个，拿 67 当分母会让每次运行都显示成"局部"。改用
新增的 `repos_in_scope`（本次纳入统计范围的仓库数）。

### 新增仓库会把它的全年历史当增量

事件库按 `first_seen_run` 判定增量，所以往 `--repos` 里加一个从没跑过的

当前未做——每次扩范围手动定一次基线成本很低，而按仓库记基线要改表结构。

## 八、每日自动运行

`daily_report.bat` 已就位（仓库根目录），日志写进 `logs/daily-<日期>.log`
（已加入 .gitignore）。

```
daily_report.bat --daily    抓取（失败重试3次），成功才推送
daily_report.bat --fetch    只抓取，失败重试3次
daily_report.bat --push     只推送（秒级）
daily_report.bat --dry      只渲染不发送
```

抓取结果写进 `logs/last-fetch-status.txt`（ok / failed），拆两个任务时
可据此判断。

### 拆分模式：抓取与推送分开（当前采用）

用户要"10:30 抓、11:00 发"。这需要推送那步不重新抓取，否则准点无从谈起。

`--resend-last` 顶替不了：它重发的是存档，不会计算新增量，抓到的新数据
不会进战报。所以新增了两个参数：

| 参数 | 作用 |
|---|---|
| `--no-notify` | 跑统计与事件留存但不推送 |
| `--only-notify` | 只算增量并推送，跳过采集管线 |

`--only-notify` 实测 1 秒完成，所以推送可以准点触发。它的底部四项累计
从上一步落盘的 `by_repo.csv` 读回，不重算也不发 API 请求；文件缺失时
整行省略而非让推送失败。

配两个计划任务：

```
schtasks /create /tn "DM日报-抓取" /tr "C:\MyCode\tools\github_contributors\daily_report.bat --fetch" /sc daily /st 10:33
schtasks /create /tn "DM日报-推送" /tr "C:\MyCode\tools\github_contributors\daily_report.bat --push"  /sc daily /st 11:03
```

时刻用 10:33 / 11:03 而非整点半点：飞书官方建议避开 10:00、17:30 这类
时刻，限流 100 次/分钟、5 次/秒。

两步之间留 30 分钟余量。抓取实测单仓库曾超过 600 秒，两仓库约 1～2 分钟，
但耗时取决于当天新提交量与网络，会浮动。若日后仓库数增加导致抓取超过
30 分钟，把两个任务的间隔拉大即可——推送那步只读库，晚跑不影响正确性。

### 为什么不做成一条链掐死推送时刻

一条链（抓完即推）也支持，就是不带参数跑。但那样推送时间随抓取耗时浮动，
今天 10:35、明天可能 10:52。用户要准点，所以采用拆分。

反过来说，若日后不在乎准点，一条链更简单，且天然不会出现"抓取失败但
推送照发旧数据"的情形——拆分模式下这是可能的，见下。

### 拆分模式的固有风险（已修复）

原先两个计划任务各跑各的，抓取那步失败时推送照常跑，发出的是上一次
成功抓取的数据——不会发假消息（增量从库里算，库没更新就是没增量），
但也不会告诉你抓取失败了。

用户指出这个风险可以避免。分三层修（`2ec8cbd`）：

一、`repos.fetch_repos` 补退避重试。实测的 `RemoteDisconnected` 正是栽在
这里：查 fork 上游的那个 `requests.get` 是裸调用，没有任何重试，而同项目的
`GitHubGraphQL` 有 5 次。现在连接层异常与 403/429/5xx 都会退避重试，
401/404 这类不重试（重试鉴权错误没有意义），重试用尽抛 `RepoFetchError`。

二、新增 `--strict-repos`。单仓库失败默认只记 `failures` 并返回 0，这是
第一期"单仓库失败不中断整体"的原则。但每天定时跑时它会让"抓取部分失败"
伪装成成功——实测撞到 `SSLEOFError` 导致 dpdata 失败，卡片底部写
"1/2 个仓库"却照常推送。打开该参数后有失败即非零退出，默认行为不变。

三、脚本层加外层重试与串联。`--fetch` 失败重试 3 次、间隔 120 秒；
`--daily` 模式下抓取成功才推送，失败到底则在日志里明确写 `SKIPPING push`
并非零退出。抓取步骤自动带 `--strict-repos`。

一天之内撞到两种不同的网络故障（`RemoteDisconnected` 与 `SSLEOFError`），
说明这个重试不是过度设计。

### API 限额的担忧不成立（更正 08-10 的记载）

08-10 交接文档记的是"单仓库 176 点，34 个约 6000 点，而 GraphQL 每小时
上限 5000"，列为待处理问题。实测 452 点，只有估算的 7.5%。

估算错在把 deepmd-kit 单仓库首次全量查询的点数直接乘以仓库数，而多数

全量，每天一次毫无压力。此问题可以结掉。

### 24 分钟对定时安排的影响

原设想"10:30 抓、11:00 发"只有 30 分钟余量，刚好卡在边缘。今天 24 分钟
是缓存齐全的情况；某天某个大仓库有大量新提交就可能超时。

两个选择：抓取提前到 10:00 留 60 分钟余量；或用 `--daily` 串联模式抓完
即推，不掐表。


若要准点推送，仍可拆两个任务，但要自己看 `logs/last-fetch-status.txt`
判断抓取是否成功：

```
schtasks /create /tn "DM日报-抓取" /tr "...\daily_report.bat --fetch" /sc daily /st 10:33
schtasks /create /tn "DM日报-推送" /tr "...\daily_report.bat --push"  /sc daily /st 11:03
```

时刻用 10:33 / 11:03 而非整点半点：飞书官方建议避开 10:00、17:30 这类
时刻，限流 100 次/分钟、5 次/秒。


### 脚本里两个不显眼但重要的地方

一、注释必须是 ASCII。cmd.exe 逐行重读批处理文件，中文注释在不同活动
代码页下会被当成命令执行——第一版加了 `chcp 65001` 反而让中文注释全部
报"不是内部或外部命令"，脚本直接死掉。

二、`PYTHONIOENCODING=utf-8` 与 `PYTHONUTF8=1` 必须设。不设的话日志里
中文全是乱码，而日志是排障用的，看不懂等于没有。这两个只作用于子进程，
批处理自身仍按原代码页解析。

另外用的是 Python 绝对路径而非 `py -3.12`：计划任务的 PATH 与交互式登录
不同，py.exe 启动器不一定找得到。

### 计划任务的两个前提

必须以当前用户身份运行——token 来自 `gh` 的 keyring，换用户取不到。
机器关机或休眠时任务不会跑，这是本机方案的固有限制，介意的话得搬
GitHub Actions。

### 周报与月报

新增 `notify/period.py`、`store.events_between`、`--weekly` / `--monthly`。

口径与日报**不同**且有意为之：

| | 判定依据 | 理由 |
|---|---|---|
| 日报 | first_seen_run | 保证不漏报——author date 是代码写成时间 |
| 周月报 | event_time | "上周发生了什么"是时间概念 |

混用会让七天日报之和对不上周报，那种数字打架最难解释。

> **2026-08-13 更新：日报改为按 `first_seen_at`（入库时间戳）锚定 10:00
> 的固定窗口。** 口径仍是入库时间（不漏报的理由不变），只是从"运行序号"
> 换成时间戳，使窗口与抓取时刻解耦。周月报口径不变。
> 详见 `2026-08-13-进度与问题交接.md`。

周月边界按东八区算再转 UTC：库里存 UTC，直接拿 UTC 日界当周界会把
周一早八点前的事件算到上一周。跨年跨月用"减一天再取该月一号"处理。

内容是汇总加排行榜（活跃贡献者、活跃仓库各前 5），不逐条列——一周
几百条会刷屏。author 为 null 的事件不进榜，否则会冒出空名字。

实测：周报 186 条事件 / 22 位贡献者（08-03~08-09），月报 1583 条 /
71 位（07-01~07-31）。两者都只读库、秒级完成，不影响日报的增量基线。

### 仓库失败的处理（按用户要求定稿）

三层，从内到外：

| 层 | 行为 |
|---|---|
| HTTP 请求 | `fetch_repos` 与 GraphQL 各自退避重试 5 次 |
| 单个仓库 | 单独重试 3 轮，间隔 60 秒，只重跑失败的那几个 |
| 仍失败 | 写进卡片，累计到明天，不拦推送 |
| 整次运行失败 | 脚本重试 2 轮（间隔 5 分钟），全败才跳过推送 |

> **2026-08-13 更新：单个仓库的重试已改为非阻塞。** 失败就地重试一次即
> 跑下一个仓库，一轮跑完再回头重跑失败的，共 3 轮（每仓库最多 6 次）。
> 固定 60 秒轮间等待会让一个仓库的抖动拖着其余 37 个干等。
> `--repo-retry-wait` 语义改为"只剩最后一个仓库时的间隔"（默认 30）。

只重跑失败的仓库而非整体重试：38 个仓库跑一次 25 分钟，整体重试会让
一个仓库的瞬时抖动拖着其余 37 个重新 fetch。

卡片文案"未能抓取：X（其增量将累计到明天的日报）"经核实为真：增量按
`first_seen_run` 判定，今天没抓到的仓库明天抓到时那些事件才首次入库。

**撤掉了抓取步骤的 `--strict-repos`**：一个仓库连不上不该让其余 37 个的
动态全都发不出去。该参数仍保留，供需要严格判定的场景用。

一天之内撞到三种网络故障（`RemoteDisconnected`、`SSLEOFError`、
`connect timeout`），说明这套重试不是过度设计。

### 计划任务（当前配置）

```
10:00  daily_report.bat --fetch     抓取入库，约 25 分钟
11:03  daily_report.bat --push      只推送，秒级
周一 11:15  daily_report.bat --weekly
每月 1 号 11:30  daily_report.bat --monthly
```

抓取与推送拆开是因为抓取耗时不可控而推送要准点。两者留一小时余量。

脚本里一个坑：`exit /b 2` 这类字面量在 `setlocal` 内不会传播到进程
退出码，必须写成 `endlocal & exit /b 2`。用变量的退出点（`exit /b !CODE!`）
不受影响，实测确认。
