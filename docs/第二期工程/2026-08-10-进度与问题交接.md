## 二、这一期在做什么

第一期的工具是一次性 CLI：跑一次，把区间内的累计结果覆盖写进输出目录，
没有历史概念，"增量"无从谈起。

第二期让它变成每天自动跑一次的常驻任务：更新总量的同时把看到的每一条
commit / PR / issue 存进事件库，算出"自上次汇报以来发生了什么"，推送到飞书群。

## 四、四条不变量（不要改回去）

一、事件不接管计数。事件表只做旁路留存，CSV 仍是排名次的唯一依据。
第一期的计数逻辑踩了四个坑才修对（时间窗按 author date、身份归并、fork 上游
排除、PR 分支重复计数），把计数改成"从事件表重算"等于把这些逻辑迁移一遍。
两套数字在 squash 场景可能对不齐，这是已知且接受的。

二、增量按"本次运行新看到的"判定，不是按事件自身时间戳。因为统计窗口按
author date 算，而 author date 是代码写成时间不是进入仓库时间。有人本地写了
两周才推上来，按事件时间判定就永远不进战报，但总量确实涨了。

三、PR 合并是状态变更而非新增行，单独记表。上周创建、今天合并的 PR，只看
新增行会漏掉，而合并恰恰是最值得说的事件。对应地，状态未变时坚决不记变更——
那是"每天重复推送同样内容"这个 bug 的唯一防线，`test_store.py` 里有专门的
测试守着（`test_unchanged_state_produces_no_change_record`）。

四、事件收集与推送失败都不改退出码。退出码只反映统计跑没跑成，计划任务与
监控盯的是它。推送失败有自愈机制（下次把两次的增量一起推），且群里没消息
自然会发现。

### 二、全量跑会撞 GitHub API 限额

> 2026-08-12 更正：实测不成立。全量跑 38 个仓库只花 452 点（剩余 4334），
> 是下面估算的 7.5%。估算错在把 deepmd-kit 单仓库的点数乘以仓库数，而
> 多数仓库很小、分页次数远低于它。每天全量跑毫无压力。以下保留原记载。

API 消耗为零。但要每天全量跑就会遇到。

缓解办法：同日重跑读缓存（点数为 0）；或分批跑；或接受偶尔撞限额后

### 三、事件库丢失不可完全重建

旧事件能重爬，但"第几次运行首次看到"这个信息重建不了——而增量正是基于它。
库文件在 `data/events.db`，已加入 `.gitignore`（派生数据且会持续增长）。
要长期历史请自行备份。

库损坏时会自动改名为 `events.db.corrupt-<时间戳>` 并重建空库，不自动删除，
万一能救。此时统计不受影响，但历史归零，之后第一次运行会跳过推送。

### 四、新增仓库会把它的全年历史当增量（2026-08-11 发现）

事件库按 `first_seen_run` 判定增量，所以往 `--repos` 里加一个从没跑过的
仓库时，它今年至今的全部事件都是"本次首次看到"，会一次性涌进战报。

实测：库里只有 deepmd-kit 时加入 dpdata，下一次的战报变成
"125 次提交 · 109 个 PR 合并 · 38 个 PR 新建 · 43 个 issue"，
全是 dpdata 的全年历史，不是当天活动。

这与首次建库是同一类问题，处置办法也一样：扩大仓库范围后先跑一次
`--mark-notified` 定基线，再开始正常推送。已写进 README 的参数说明。

彻底的修法是按仓库分别记基线（新仓库首次出现时自动跳过其历史），
当前未做——每次扩范围手动定一次基线成本很低，而按仓库记基线要改表结构。

## 八、几个容易踩的坑

解释器是 Python 3.12，不是系统默认的 3.14——后者没装 pytest。
`py -3.12` 前缀不能省。

Git Bash 里的 `/tmp` 是虚拟路径，传给 Python 会变成字面量 `C:\tmp`。
调试时用 `%TEMP%` 或绝对路径，否则会在错误的位置建出空文件。

`collect_api_events` 按"今天"的日期找 API 缓存。缓存是隔天失效的，
所以 `--no-fetch` 模式或跨天重跑时事件只有 commit 没有 PR/Issue。
这是有意的：不为附带产物额外发请求增加限额压力。

飞书请求体上限 20 KB，卡片渲染超 18 KB 时逐级降级（10 → 5 → 3 → 1 条）。
降级顺序是减条数而非砍标题——少列几条仍可读，标题砍半截会看不懂。

飞书限流 100 次/分钟、5 次/秒，官方文档建议避开 10:00、17:30 这类整点
半点。配计划任务时时间点错开整点。

`.env` 已在 `.gitignore` 中。日志里打印 webhook URL 一律走 `feishu.mask()`
脱敏，只显示末四位，否则日志文件会变成凭据泄露源。
