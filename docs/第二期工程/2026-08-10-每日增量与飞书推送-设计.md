# 第二期设计：每日增量统计与飞书推送

日期：2026-08-10
状态：设计已确认，待实现
前置：第一期已完成，详见 `README.md` 与 `docs/第一期工程/2026-07-29-任务交接.md`

## 一、要解决什么

第一期的工具是一次性 CLI：跑一次，把 `--since` 到 `--until` 区间的累计结果覆盖写进
输出目录。它没有历史概念——上一次的结果被覆盖，所以"增量"无从谈起。

第二期要让它变成每天自动跑一次的常驻任务：在更新总量的同时记录增量，并把增量
推送到飞书群。

## 二、需求确认结论

设计前与用户逐条确认的结果，是后续所有取舍的依据。

| 项 | 结论 | 理由 |
|---|---|---|
| 增量形态 | 事件明细旁路留存 | 只存快照差值的话，推送内容只有干巴巴的数字，很快没人看 |
| 是否接管计数 | 不接管 | 第一期的计数逻辑踩了四个坑才修对，迁移有回归风险 |
| 事件作者 | 存原始 login，不归并 | API 侧白拿，成本近零；不存的话以后想要得重爬 |
| 推送是否显示人名 | 不显示 | 用户明确：感兴趣的人会自己点进去看 |
| 运行环境 | 先本机每天跑一次 | 缓存与 token 都在本机，零配置；Actions 要重建 3 GB 缓存 |
| 出口 | 飞书自定义机器人 webhook | 群主自己就能加，不需要企业管理员审批 |
| 推送内容 | 战报型：今天发生了什么 | 用户选定 |
| 增量判定 | 按"本次运行新看到的" | 保证不漏报，详见第四节 |

## 三、架构

### 模块划分

第一期的依赖是严格单向的，第二期保持这个性质。新增四个模块：

```
__main__ → main → ┬→ (第一期七个模块，不动)
                  │
                  ├→ events    ── 采集侧：从两条管线顺带收集事件
                  ├→ store     ── 存储侧：SQLite 读写、去重、差集
                  └→ notify/   ── 消费侧
                       ├→ digest    ── 从库里读出本次新增，组织成战报数据
                       ├→ card      ── 战报数据渲染成飞书卡片 JSON
                       └→ feishu    ── 签名、POST、重试
```

关键约束：`store` 不知道飞书存在，`notify` 不知道 git 和 API 存在。两边只通过库里的
表通信。以后加网页看板或多维表格，是在 `notify/` 旁边加一个平级消费者，`store` 一行
不用改。

| 模块 | 职责 | 不做什么 |
|---|---|---|
| `events.py` | 定义事件数据类；从两条管线的中间结果提取事件 | 不写库、不判断新旧 |
| `store.py` | 建表、upsert、返回新增与状态变更、查询 | 不知道事件从哪来、不知道推给谁 |
| `notify/digest.py` | 按 run 查出新增与状态变更，聚合成战报结构 | 不涉及任何飞书概念 |
| `notify/card.py` | 战报结构转飞书卡片 JSON | 不发网络请求 |
| `notify/feishu.py` | 签名、POST、失败重试 | 不关心卡片内容 |

`card` 与 `feishu` 分开是有意的：卡片渲染是纯函数，可完全离线测试；网络那部分单独
隔离，测试时 mock。这与第一期 `output.py` 是纯函数的思路一致。

### 采集侧如何接入

不改 `collect_api_stats` 与 `collect_git_stats` 的签名和返回值——它们是第一期四个
缺陷的修复现场，动它们风险最高。做法：

- git 侧：解析循环已在逐条遍历 commit，加一个 append 成本近零，直接在循环里收集。
- API 侧：需在 GraphQL 查询补 `number` / `title` / `url` / `state` 字段，改动本就落在
  查询串上，顺手把节点数据留下。

两侧遵守同一条原则：事件收集失败不得影响统计。用 try 包住，失败记 warning、事件为空，
CSV 照常输出。这是第一期"单仓库失败不得中断整体"原则的延伸——新功能不能拖累旧功能。

## 四、数据模型

SQLite 单文件，默认 `./data/events.db`。选 SQLite 而非 CSV 追加的理由：要按主键去重，
CSV 每次得全表扫；且以后网页看板要按时间范围查询，SQL 天然合适。SQLite 单文件、零
部署、Python 内置，无额外依赖。

### events —— 事件明细，只增不改

| 列 | 类型 | 说明 |
|---|---|---|
| `event_key` | TEXT 主键 | 全局唯一键，构造见下 |
| `kind` | TEXT | commit / pr / issue |
| `repo` | TEXT | 仓库名 |
| `number` | INTEGER | PR/Issue 编号，commit 为空 |
| `sha` | TEXT | commit SHA，PR/Issue 为空 |
| `title` | TEXT | PR/Issue 标题；commit 取提交信息首行 |
| `url` | TEXT | 网页链接 |
| `author_login` | TEXT | 原始 login，拿不到时为空 |
| `event_time` | TEXT | 事件自身时间，UTC ISO |
| `state` | TEXT | PR 专用：open / merged / closed；其他为空 |
| `first_seen_run` | INTEGER | 首次被看到的运行 id，外键指向 runs |

`event_key` 构造：commit 用 `commit:{repo}:{sha}`，PR 用 `pr:{repo}:{number}`，issue 同理。
SHA 全局唯一，但同一 commit 可能出现在多个仓库（fork），故带上 repo。

用 `first_seen_run` 而非 `first_seen_at`：运行 id 能直接关联那次运行的完整上下文
（时间窗、参数），时间戳从 runs 表 join 就有。

> **2026-08-13 更新：这个决定已被推翻。** 只有运行序号就无法按固定时间窗切日报，
> 内容会随抓取时刻变化——重跑一次抓取，当天日报的内容就不一样了。现已加上
> `first_seen_at` 列（两者并存），日报按它锚定 10:00 的固定窗口。
> 详见 `2026-08-13-进度与问题交接.md` 第三节。

不存 commit 的 diff 与文件列表：战报用不上，YAGNI。

### runs —— 每次运行一行

`run_id` 自增、`started_at`、`finished_at`、`since`、`until`、`repos_processed`、
`new_events`、`notified`、`status`。这张表让"第 N 次运行新增了什么"可查，也是排障依据。

### event_state_changes —— 状态变更

PR 不是一次性事件：今天创建、后天合并，`event_key` 不变但 state 变了。所以
`events.state` 存当前状态，变更历史单独记一行（`event_key`、`old_state`、`new_state`、
`run_id`）。

这张表解决整个设计里最容易被忽略的问题：如果只把"新增行"当增量，那么一个上周创建、
今天合并的 PR，今天的战报里根本不会出现。而合并恰恰是社区最关心的事件。

### 库文件不进 git

已加入 `.gitignore`。它会持续增长，且是可重建的派生数据。但要在文档里提醒：旧事件
能重爬，而"第几次运行首次看到"这个信息重建不了，需自行备份。

## 五、数据流

### 一次运行的时序

```
1. 第一期流程照跑（采集 → 计数 → 写 CSV）      ← 不动
2. store.begin_run() 开一条 runs 记录，拿到 run_id
3. 两条管线收集的事件 → store.upsert_events(events, run_id)
   返回：新增了哪些、哪些状态变了
4. store.finish_run(run_id, 统计数字)
5. 若 --notify：digest.build() → card.render() → feishu.send()
6. store 记录 notified 结果
```

### 增量如何判定

按"本次运行新看到的"判定，而非按事件自身时间。

理由：第一期的时间窗按 author date 算（这是踩坑后特意改的），而 author date 是代码
写成时间，不是进入仓库时间。有人本地写了两周才推上来，这批 commit 的 author date 全是
两周前——按事件时间判定，它们永远不会出现在任何一天的战报里，但总量确实涨了，总量与
战报对不上。按"新看到"判定则保证不漏。

代价：战报里可能出现日期是两周前的 commit，在卡片上标注真实日期即可。

### 推送失败的自愈

`digest` 查询的不是"本次 run"，而是"上一次成功推送之后的所有 run"。这样昨天推送失败，
今天会把两天的内容一起推出来，不需要额外的重试队列。

### 首次运行

库为空时，今年至今几千条事件都会被判为新增。此时只建库不推送，日志里说明。实现上：
runs 表里没有已完成记录时跳过推送。从第二次运行开始才有真正意义的增量。

### 空转不推送

本次无任何新增时（周末常见）不推送。每天推一条"今天没有新增"会很快让人把机器人静音。
可用 `--notify-empty` 打开。

## 六、战报内容

```
【DeepModeling 社区日报】2026-08-10

自上次汇报（8-09 10:00）以来：
新增 12 次提交 · 5 个 PR 合并 · 3 个 PR 新建 · 2 个 issue

── 合并的 PR ──
· deepmd-kit #4321 支持 XX 格式的模型导出
· abacus-develop #1567 修复 YY 条件下的收敛问题

── 新建的 PR ──
· deepmd-kit #4325 ...

── 新增 issue ──
· abacus-develop #890 ...

今年至今：366 位贡献者 · 2527 次提交
```

设计决定：

- 顶部一行汇总数字，因为群消息大多数人只看前两行。
- 写"自上次汇报以来"而非"今天"，这是增量判定方式的诚实表述：昨天推送失败时，这句
  会写"自 8-08 以来"。
- PR/Issue 列表带链接，标题直接可点。commit 不逐条列（一天几十条会刷屏），只给数字。
- 底部一行今年累计，把第一期的统计成果带上。
- 每类最多列 10 条，超出显示"…还有 N 条"。首次运行或长期未跑后重跑，可能一次涌进
  几百个事件，不截断会撑爆群消息，飞书卡片本身也有大小限制。
- 日期显示转东八区，库里存 UTC。存储用绝对时间，展示用本地时间。

## 七、错误处理

第一期原则"单仓库失败不得中断整体"扩展为分层：每一层失败，都不许影响比它更已确立的
成果。

| 层 | 失败时 | 退出码 | 理由 |
|---|---|---|---|
| 统计（第一期） | 单仓库失败记入 failures，整体继续 | 原有 | 不变 |
| 事件收集 | 该仓库事件为空，记 warning | 不变 | 新功能不能拖累旧功能 |
| 事件入库 | 记 error，统计已落盘不受影响 | 不变 | CSV 是主产物，库是派生 |
| 推送 | 记入 runs.notified=false，下次补推 | 不变 | 通知失败不是数据失败 |

全都不改退出码是有意的：退出码只反映统计有没有跑成功，计划任务与以后的监控会盯着它。
推送失败不该触发"数据出问题了"的报警——它有自愈机制，且真出问题时群里没消息自然会
发现。

盲区与对策：推送连续失败多天可能不被察觉。日志里显式打出"距上次成功推送已 N 次运行"，
N 超过 3 打 error 级别。不做额外告警通道（告警通道本身也会失败，是套娃问题）。

### 具体失败场景

SQLite 库损坏（断电、磁盘满）：启动时做一次 `PRAGMA integrity_check`，失败则把文件
重命名为 `events.db.corrupt-<时间戳>` 并重建空库。统计不受阻，代价是历史丢失。不自动
删除损坏文件，留着万一能救。

飞书 webhook 失败分两类：网络层（超时、连接失败）重试 3 次，指数退避 1s/2s/4s；应用层
（飞书返回错误码，如签名错、机器人被移除、频率限制）不重试，直接记录错误码。重试一个
签名错误没有意义。

卡片过大：除每类截断 10 条外，渲染完检查 JSON 字节数，超阈值逐步降级（先砍标题长度，
再减条数），保证消息一定发得出去而不是整条丢失。

GitHub API 限额：事件收集要在 GraphQL 补字段，会增加每次查询的点数消耗。实现后必须
重测 `api_points_spent`，确认没有把"每天一跑"变成会撞限额的操作。这是实现阶段的必验项。

## 八、凭据

`FEISHU_WEBHOOK_URL` 与 `FEISHU_WEBHOOK_SECRET` 走环境变量或 `.env`，不进代码、不进
文档、不进库。`.env` 已加入 `.gitignore`。

日志里打印 webhook URL 时做脱敏，只显示末四位，否则日志文件会变成凭据泄露源。

这与第一期 GitHub token 走 `gh auth token`、不落盘的处理保持一致。

## 九、CLI 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--events-db` | `./data/events.db` | 事件库路径 |
| `--no-events` | 关 | 跳过事件留存，退回第一期行为 |
| `--notify` | 关 | 跑完推送飞书 |
| `--notify-dry-run` | 关 | 渲染卡片打到 stdout，不发送 |
| `--notify-empty` | 关 | 无新增时也推送 |

默认不推送是有意的：推送有外部副作用，应显式开启。计划任务里才带 `--notify`。
`--no-events` 是逃生舱，出问题能一键退回第一期行为。

## 十、测试策略

沿用第一期约定：全部离线，与源码模块一一对应。

`store.py` 用 `:memory:` 内存库，不落盘、不需要 fixture。关键行为：

- 同一 `event_key` 写两次，第二次不产生新增（去重生效）
- PR 从 open 变 merged，events.state 更新且 event_state_changes 多一行
- PR 状态没变时不产生多余变更记录——这是"每天重复推送同样内容"这个 bug 的唯一防线
- 跨多次 run 查询"上次成功推送之后的全部新增"，结果正确

`events.py` 用固定样本测提取，重点测边界：标题含换行、标题极长、`author.login` 为 null
（实测 API 常返回 null）、commit message 为空。

`notify/card.py` 是纯函数，最好测：条数超限正确截断、空列表不渲染该分区、超大内容触发
降级、日期正确转东八区。不需要任何 mock。

`notify/feishu.py` mock 掉网络：测签名算法（按飞书文档实现并用已知输入输出验证）、
网络超时触发重试、应用层错误码不重试。

端到端沿用 `test_integration.py` 的路子：小规模伪造数据走完整流程，`feishu.send` 被 mock。

### 测试测不出来的部分

签名算法与卡片能否被飞书接受，只有真发一次才知道。单元测试只能保证代码按我理解的规则
跑，不能保证对文档的理解是对的。实现阶段必须有一步：`--notify-dry-run` 看 JSON，再往
真实群里发一条测试消息。

建议先用只有自己的测试群调通，再换正式群，避免调试消息污染社区群。

### 第一期的回归防线

第二期会碰 `git_stats.py` 与 `api_stats.py`，这两个文件里长着第一期修过的四个缺陷。
因此：

改动前跑 `pytest -m "not network"` 确认 299 passed，改完必须仍是 299 passed（加新增的）。
任何原有测试变红都说明碰坏了第一期的正确性，停下来查，不要顺手改测试。

比单元测试更硬的证据：改动前留一份 `output_all/summary.csv`，改完用同样参数
`--no-fetch` 重跑（秒级），两份应逐字节相同。这直接证明第二期没有影响第一期的输出。

## 十一、明确不做的事

- 不接管第一期的计数逻辑，事件表只旁路留存
- 不做身份归并，事件只存原始 login
- 不存 commit 的 diff 与文件列表
- 不做网页看板与多维表格（以后作为 `notify/` 的平级消费者接入）
- 不搬 GitHub Actions（等本机跑顺再说）
- 不做独立告警通道
