## 一、统计范围

### Q1. fork 仓库是否纳入表彰？

组织下 67 个仓库中有一部分是 fork。需要区分两种：

- self fork：fork 自组织内部其他仓库，例如 abacus-develop。这类实质是
  社区自己的开发主线，抽查中它贡献了 178 位贡献者、3466 次提交。
- external fork：fork 自外部上游项目。这类仓库里的提交可能大部分来自
  上游原作者，而非本社区成员。

工具已实现 commits_not_in_upstream 列，能算出"排除上游后真正属于本社区
的提交数"，所以两种口径都支持。

建议：纳入 self fork，排除 external fork。需确认是否认可。

### Q2. 超大仓库 sciencepedia（17.6 GB）是否纳入？

该仓库体积远超其他仓库，纳入会显著拉长首次运行时间与磁盘占用。如果它
主要是数据/文档而非代码协作，排除对表彰名单影响不大。

需确认：这个仓库是否有需要表彰的贡献者活动？

### Q3. 正式统计的时间区间是什么？

抽查用的是 2026-01-01 起至今，仅为验证工具。正式出名单需要明确区间，
例如自然年、财年、或项目启动至今。

## 二、统计口径

### Q4. 按代码写成时间还是合并时间统计？

这两个口径在 PR 协作场景下差别明显。工具目前按 author date（代码最初
写成的时刻）实现。

- author date：统计"这段时间写了哪些代码"。
- committer date：统计"这段时间合并了哪些工作"。启用 squash 或 rebase
  合并的仓库，每个 PR 落到主干时该时间会刷新为合并时刻。

影响：一个跨年末的 PR，两种口径会落进不同的年度。

需确认：当前的 author date 口径是否符合预期。

### Q5. 代码行数是否纳入评价？

工具可选输出 additions / deletions / files_changed。但行数容易被生成
文件与数据文件污染，且删除冗余往往比新增更有价值，因此输出中已附带
"不宜用于排名"的提示。

需确认：名单中是否需要保留行数列，若保留是否仅作参考而不排名。

### Q6. 非代码贡献如何计入？

抽查中有 81 位贡献者提交次数为零，但有评审、提 issue 或参与讨论的记录。
另有人虽写代码但主要价值在评审，例如 mohanchen 提交 117 次却有 345 次
PR 评审。三个仓库合计 1010 次 PR 创建、2105 次 PR 评审。

工具已分列输出五项：PR 创建 / PR 合并 / PR 评审 / issue 创建 / issue 评论。

查看方式：在 summary.csv 里按 commits 列筛选 0，即为这 81 人；他们的
pr_reviewed 与 issue_created 列可见其实际贡献。

需确认：这些贡献是否纳入表彰，以及各项之间是否有权重差异。

## 三、身份归并

### Q7. 需要人工确认的身份映射

贡献者若用未在 GitHub 登记的邮箱提交，系统查不到其账号，会被拆成独立
条目。同仓库内姓名完全相同且只对应一个账号的已自动合并（例如 Han Wang
的 1151+110 两条、dyzheng 的 128+278 两条），剩下 26 条需人工确认，
完整清单见 unmatched.csv。

最重要的一条：

| 条目 | 提交数 | 疑似对应账号 | 依据 |
|---|---|---|---|
| abacus_fixer (mohanchen@pku.eud.cn) | 756 | mohanchen | 邮箱域名 edu 拼写为 eud，故查不到账号 |

这是 abacus-develop 第二大提交量。若确认为 mohanchen，他的实际提交数应为
约 872 次，而非 summary.csv 当前显示的 117 次。姓名不同，自动规则刻意不
合并以避免误并，所以必须由人确认。

其余条目按性质分三类，均在 unmatched.csv 中按提交数降序排列：

| 类型 | 例子 | 说明 |
|---|---|---|
| 有真实姓名，但名单中无同名账号 | Fei Yang (60)、liwentao (17)、Erdong Sun (13) | 可能未注册 GitHub，或注册名与提交姓名不同 |
| 同一人用了多台机器 | jianrui geng 的 login-01 与 login-02 两条邮箱 | 姓名相同但两条都无账号，规则不敢合并 |
| 未配置 git 身份留下的默认值 | root、test@test.com、you@example.com、agent@example.com | 背后是真人，但从邮箱无法判断是谁 |

另有 njzjz2008@gmail.com 与 openclaw@njzjz.win 两条显示为 OpenClaw，
疑似与 njzjz 相关，也需确认。

unmatched.csv 的列为 identity（邮箱或提交者标识）、name（git 中的姓名）、
commits、repos（出现在哪些仓库）、pr_created、issue_created、guess
（系统猜测的同名账号，本次全为空）。

需确认：abacus_fixer 是否为 mohanchen；其余条目请熟悉社区成员的同事过
一遍，能认出的直接在 guess 列填上对应 GitHub 账号即可。

## 附：运行成本参考

- 抽查 3 个仓库耗时约 10 分钟，缓存 63 MB，主要耗时在克隆。
- 全量约 40 余个仓库预计 1 至 2 小时、2 至 3 GB。
- 建立缓存后重算无需重新克隆：纯 commit 口径的调整（改时间窗、改 fork
  范围）可完全离线，秒级完成；涉及 PR 与 issue 的重算需要访问 GitHub
  API，但结果有缓存，仍远快于首次运行。

因此上述问题可以先确认再跑全量，也可以先跑全量再按确认结果重算，
两种顺序都不会产生重新克隆的成本。
