## 一、结论摘要

项目整体结构清晰、职责边界干净、异常处理到位，注释解释的是「为什么」而非
「做什么」，这在这类爬取工具里少见。测试覆盖 283 个用例，关键口径（时间窗、
身份归并、bot 判定、fork 上游排除）都有针对性用例固化。

但实测发现一个会显著改变榜单结果的缺陷（P0），以及一个同类但影响较小的
缺陷（P1）。两者根因相同：`git log --all` 的语义比设计意图更宽。

| 级别 | 问题 | 影响 |

## 二、P0：refs/pull 导致提交重复计数

### 现象

`clone --mirror` 的 refspec 是 `+refs/*:refs/*`，GitHub 在服务端暴露
`refs/pull/<n>/head`，因此镜像克隆会把每个 PR 的原始分支一并抓下来。
`git log --all` 遍历 `refs/` 下全部引用，这些 PR 分支提交全部计入。

abacus-develop 实测（窗口 2026-01-01 起）：

| 口径 | 窗口内提交数 |
|---|---|
| `--all`（当前实现） | 3535 |
| `--branches --tags` | 425 |
| 仅存在于 refs/pull | 3110 |

该仓库 `refs/pull/**` 共 4934 个引用。

### 为什么这是重复而不是补充

abacus-develop 用 squash 合并。PR #7702 在 `develop` 上是一条
`Refactor init_esolver factory interface (#7702)`，作者 `费扬`；
而 `refs/pull/7702/head` 上有作者 `Fei Yang <2501213217@stu.pku.edu.cn>`
的同名原始提交，SHA 不同，`develop` 不可达。同一份工作被计两次，且两次的
邮箱不同 —— 一次是 noreply 可解析出 login，一次是学校邮箱解析不出，
于是同一个人还会被拆成两行。

`README.md` 里写的「按 commit SHA 天然去重」只保证同一 SHA 不重复，
squash 产生的是新 SHA，去重机制对它无效。

### 影响范围

已在 output_all 上逐条校验，完整结果见
`docs/2026-07-31-output_all数据校验.md`。要点：

34 个仓库，窗口内提交总数 13189（`--all`）对 5687（`--branches --tags`），
独立邮箱 304 对 152。其中 152 个邮箱主干零提交 —— 恰好一半的身份纯由
PR 分支产生。

主榜单虚高倍数：

| 现排名 | 姓名 | 现显示 | 主干实际 | 虚高 |
|---|---|---|---|---|
| 1 | Han Wang | 1307 | 130 | 10.1× |
| 2 | Mohan Chen | 872 | 68 | 12.8× |
| 5 | dyzheng | 411 | 25 | 16.4× |
| 8 | Xuwznln | 319 | 308 | 1.04× |

按主干重排，第一名是现排第 8 的 Xuwznln（308 次）。`q434343`、
`AsymmetryChou`、`Zikkying` 等提交几乎全在主干的人被挤到名单后段。

Q7 确认的「abacus_fixer 即 mohanchen」这个身份结论正确，但 872 这个数字
不能用。`docs/2026-07-30-全量统计结果报告.md` 已加作废警示。

### 可选的修法（未实施）

三条路线，语义不同，需要业务判断而非技术选择：

1. 改用 `--branches --tags`。只统计仓库自己的分支与标签，
   最接近「进入代码库的工作」。缺点是未合并 PR 的工作不计。
2. 保留 `--all` 但排除 `refs/pull/*`：
   `git log --no-merges --exclude=refs/pull/* --all`。等价于第 1 条，
   但会额外保留 `refs/remotes/*` 等其他引用。
3. 保留 `--all`，另加基于「作者 + 提交主题 + 改动指纹」的跨 SHA 去重。
   能同时算上未合并 PR 的努力，但去重规则本身有误判风险。

我倾向第 1 条：`--branches --tags` 语义明确、无需启发式规则。若要认可
未合并 PR 的工作，宜作为单独一列而非混进 `commits`。

无论选哪条，`README.md` 的「分支」口径段落与全量报告的数字都要同步更新。

## 三、P1：upstream remote 混入 fork 的 commits 列

`count_upstream_excluded` 会 `git remote add upstream` 并 fetch 到
`refs/remotes/upstream/*`。这些引用留在缓存里，于是从第二次运行起，
`collect_git_stats` 的 `git log --all` 就会把上游独有的提交计入 `commits`。

GPUMD 实测：`--all` 638 次，`--branches --tags` 624 次，差出的 14 次
只存在于上游分支上（作者 Liangting 4 次、XU Ke 3 次、duanzaixu 3 次、
Paul Erhart 2 次等）。这 14 个人的提交从未进入本组织的 fork。

这个缺陷有个隐蔽特征：首次运行时 upstream remote 还不存在，结果是对的；
第二次运行才出现偏差。缓存复用是本项目的核心卖点，所以实际使用中几乎
一定会踩到。当前 5 个 fork 缓存（abacus-develop、deepflame-dev、dflow、
dpgen2、GPUMD）都已有 upstream refs。

`commits_not_in_upstream` 列不受影响 —— 它显式带了
`--not --remotes=upstream`。受影响的只有 `commits` 列。

P0 若按第 1 条修，此问题一并解决（`--branches --tags` 不含 remotes）。

## 四、P2：磁盘预检估算偏差

`cache.py` 的 `_SIZE_FACTOR = 0.6`、`_HEADROOM = 1.2`，按 GitHub 标称
体积推算所需磁盘。但统计走 `--filter=blob:none`，实际下载量与标称体积
基本无关：sciencepedia 标称 17.5 GB，缓存实占 412 MB，实际系数 0.023 —— 
偏差 26 倍。

后果：新设备首次全量运行，预检会算出约 20 GB 需求，磁盘不足 20 GB 时
直接以退出码 2 拦下，而真实需求约 550 MB。有缓存时不触发（`estimate_needed_mb`
只统计未克隆的仓库），所以本机跑不出来。

`--count-lines` 走完整克隆，那时高系数才合理。建议按 `cfg.count_lines`
分别取系数（不统计行数时约 0.05，统计时保留 0.6）；或把预检降级为警告
而非硬拦截。`快速开始.md` 里已写明遇到误挡时的绕法。

## 五、P3：GraphQL 子连接固定 50 条

`PR_QUERY` 里 `reviews(first:50)`、`comments(first:50)`、`commits(first:50)`
都不翻页，也不检测 `hasNextPage`。达到上限时静默截断。

在 23 MB 的 API 缓存上实测：

| 子连接 | 达到 50 条上限的节点数 | 总节点数 |
|---|---|---|
| PR commits | 686 | 26090 |
| PR reviews | 35 | 26090 |
| PR comments | 0 | 26090 |
| Issue comments | 0 | 9314 |

`commits` 只用于顺带收集 email→login 映射，截断意味着少拿一部分映射，
后果是多出几个本可关联的 `unmatched` 条目，不会算错计数。`reviews` 截断
会少记 `pr_reviewed`，35 个 PR 属可接受量级，但机制上是静默丢数据，
与项目「永不静默丢数据」的原则不一致。

`MAX_PAGES = 400` 的顶层翻页上限是有警告的，做得对。abacus-develop 实测
需要 302 页，已经接近上限，值得留意 —— 换个更大的组织或更长的窗口会撞上。

## 六、P4/P5：归并的两个边角

P4：`summarize` 建行时用第一条遇到的 `Row` 做模板，`name` 因此取的是
「首个仓库里的名字」而非最完整的名字。实测 13 人在不同仓库有不同 name，
summary 里 `liuyuxiang92` 显示 `Yuxiang Liu`（这次运气好），但
`SchrodingersCattt` 显示 `MatMaster`、`iProzd` 显示 `Duo`。若首个仓库里
恰好是 `root`，表彰名单上就会出现 `root`。建议在合并时优选「含空格、
非纯小写、非 login 相同」的候选名。

P5：无 login 的行在 `summarize` 里按 `email:` 聚合，跨仓库合并。
占位邮箱因此把不同的人并成一人 —— 实测 `test@test.com` 在 deepmd-kit
（name=`Test`）与 Uni-Lab-OS（name=`test`）各 1 次提交，被并成一行。
量小，但机制上应把 `test@test.com`、`you@example.com`、`root@localhost`
这类占位邮箱列入不合并名单。

另有 3 条记录的 `email` 列不含 `@`（`pxlxingliang`、`a-006`），说明
提交者的 git 配置里 email 字段填的是用户名。`normalize_email` 不校验
格式，原样保留 —— 这个处理是对的（宁可保留也不丢），但值得在文档里说明。

## 七、P6/P7：未实现参数与工程化缺口

`--jobs` 与 `--verbose` 在 `config.py` 里定义并进了 `Config`，但
`contributors/` 里没有任何地方读取它们。用户传 `--jobs 8` 无任何效果
也无提示。建议要么实现，要么从 CLI 移除。

`--jobs` 若要实现：仓库间的 clone/fetch 可以并行，但 GraphQL 调用共享
额度、`IdentityResolver` 有跨仓库状态，需要加锁或改成先并行采集再串行
归并。收益（当前全量 45 秒）不一定值得这个复杂度。

`cache.py` 的 `load_progress` / `save_progress` 有实现和测试，但主流程
从未调用 —— 断点续跑实际靠 git 缓存本身完成。`models.py` 的
`Contributor` 类同样只被测试引用。都是无害死代码，可删可留。

发布前的工程化缺口：

- 无 `LICENSE`。公开仓库没有许可证等于保留全部权利，别人不能合法使用。
- 无 `pyproject.toml`。`pytest -m "not network"` 依赖的 `network` 标记
  未注册（当前无用例真的打了这个标记，所以不报警告，但约定是虚的）。
  也无法 `pip install .`。
- `.claude/settings.local.json` 被 git 追踪。文件名带 `local` 通常应
  忽略，且内容是本机权限白名单，对他人无意义。
- `requirements.txt` 把 `pytest` / `responses` 与运行时依赖混在一起。
  建议拆出 `requirements-dev.txt`，或用 `pyproject.toml` 的 optional
  dependencies。
- 依赖未固定上界。`requests>=2.31` 这类写法在长期不动的工具里可能因
  上游破坏性更新而失效。
- `shutil.rmtree(onexc=...)` 需要 Python 3.12+（3.12 之前是 `onerror`），
  `datetime.fromisoformat` 解析 `Z` 需要 3.11+。文档未写明最低版本。

## 八、做得好、不要改回去的地方

这些是实测踩坑后的结果，改回「更简洁」的写法会重新引入 bug：

- 时间窗在 Python 侧按 author date 过滤，不交给 `git log --since`。
  后者是 committer date 口径且会截断遍历。
- `git log` 字段分隔符用 `\x1f` 而非 `\x00`。Windows 的 CreateProcess
  不允许参数含 NUL 字节。
- `discard` 用 `onexc` 回调清只读位，不用 `ignore_errors=True`。
  后者在 Windows 上会留下含 `objects` 的空壳目录，让后续 clone 报错。
- `build_rows` 用 `None` 区分「上游对比失败，无从判断」与「对比成功但
  无人独立于上游」。混为一谈会把上游原作者记成满额本社区贡献。
- `is_bot` 刻意不检查 email 参数，且禁止子串匹配。`botelho`、
  `mycopilotfan@example.com` 都是真人。
- CSV 写 `utf-8-sig`。没有 BOM，Excel 打开中文姓名乱码。
- 单仓库失败记入 `failures` 并继续，不中断整体。
- `unmatched.csv` 附带姓名、提交数、所在仓库并按提交数降序。只给邮箱的
  话无法认人。

## 九、建议的处理顺序

1. P0 与 P1：决定 `commits` 的分支口径。这会改变已发布的全量数字，
   需要先确认业务口径，再改代码、补测试、重跑、更新 README 与全量报告。
2. P7 的 `LICENSE` 与 `.claude/settings.local.json`：发布前必做，成本低。
3. P2：改系数或降级为警告。影响新设备首次体验。
4. P3 的 `reviews` 翻页、P4 的 name 优选、P5 的占位邮箱名单：
   数据质量改进，可排在后面。
5. P6：删掉未实现的参数，或标注为「预留」。
