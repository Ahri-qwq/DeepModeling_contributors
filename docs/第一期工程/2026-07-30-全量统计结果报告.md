## 六、33 个跳过仓库的构成

组织共 67 个仓库，处理 34 个，跳过 33 个。跳过分三类：

| 原因 | 数量 |
|---|---|
| pushed_at 早于统计起点 | 23 |
| fork 上游为 external，按 `--include-forks=self` 排除 | 6 |
| fork 上游为 tooling，按 `--include-forks=self` 排除 | 4 |

external 六个：ADMP、GPUMD、fealpy、lammps、msys、plumed2。
tooling 四个：abacus-code-reviewer、argo-workflows、deepmd-kit-recipes、
get-changed-files —— 这些是别人写的通用 CI 组件的 fork，统计会把上游作者
算成本组织贡献者，故整仓排除。

要注意 `should_skip` 中 fork 判断先于 pushed_at 判断，所以一个仓库同时满足
两个条件时只记录 fork 那条原因。实际查这 10 个 fork 的 pushed_at，
只有 GPUMD（2026-06-09）落在窗口内，其余 9 个最后推送都在 2024–2025 年。
也就是说 fork 类里唯一因分类判断而未纳入的活跃仓库是 GPUMD，
另外 9 个 fork 无论如何调整分类都跑不出窗口内数据。lammps 与 plumed2
都在这 9 个之列（最后推送均为 2024-04-11），即便改判为社区项目也不会改变结果。

## 七、口径说明

- 统计区间 2026-01-01 ~ 2026-07-31，UTC，含两端，按 author date 过滤
- 提交数两个并列口径：`commits` 走 `--branches --tags`（只数合并进主干的）；
  `commits_loose` 额外一趟取 PR 分支上主干不可达的提交。两者均排除合并提交。
  本报告排名一律按 `commits`
- fork 仓库只统计上游为本组织的（`--include-forks self`）；
  判断 fork 实际投入用 commits_not_in_upstream 列，不要用 commits
- 不统计代码行数
- self 组织白名单五个：deepmodeling、abacusmodeling、dptech-corp、
  deepflamecfd、mzjb
- 不设仓库体积上限（`--max-repo-size 0`，即新默认），sciencepedia 因此纳入
- 本次 API 点数消耗为 0，全部命中 `.cache/` 缓存

### 出名单时该用哪个口径

两列都不是唯一正确答案，各有一处已知偏差：

- `commits`（主干）会漏掉署名邮箱与 GitHub 账号对不上的人，也会让 squash
  合并为主的仓库（abacus-develop、deepmd-kit）里的贡献者显得偏低。
- `commits_loose`（主干 + PR 分支）在 squash 场景下同一份工作被计两次，
  含重复计数，且会把 squash 前的原始作者与合并者同时算上。

建议：出表彰名单用 `commits`，它反映的是「确实合入了主干的工作」；
需要看某人的全部活动痕迹（包括未合入的尝试）时看 `commits_loose`。
两列差值大的人值得人工看一眼——可能是 squash 合并，也可能是邮箱未关联。
非代码贡献（PR 评审、issue）不受这个口径问题影响，可直接使用。

测试 299 项全部通过（`pytest -m "not network"`），其中 5 项覆盖人工映射机制，
3 项覆盖体积上限的新默认与显式设限行为。
