# 新设备快速开始

面向第一次在一台新机器上跑这个项目的人。按顺序做完即可产出完整名单。
全程约 15–25 分钟，其中大部分时间在等克隆。

## 零、这个工具会在你机器上做什么

先说清楚，免得后面发现意外：

- 往 `./.cache/repos/` 克隆目标组织的全部仓库（裸库，只取提交元数据）。
  一年窗口约 550 MB。
- 往 `./.cache/api/` 写 GitHub API 响应缓存，约 25 MB。
- 往 `./output/` 写结果文件。
- 消耗 GitHub API 额度（GraphQL）。全量一次约几千点，配额是每小时 5000 点，
  正常够用；同日重跑读缓存不再消耗。
- 不写任何系统目录，不改 git 全局配置，不把 token 写进缓存
  （clone 走匿名访问）。

想换缓存位置用 `--cache-dir`，换输出位置用 `--out-dir`。

## 一、装环境

### 1. Python 3.12 或更高

必须 3.12+。项目用了 `shutil.rmtree(onexc=...)`，这个参数在 3.12 才有。

```bash
python -V     # 期望 Python 3.12.x 或更高
```

### 2. git

```bash
git --version
```

没有的话去 https://git-scm.com/downloads 装。Windows 上装完要确认
`git` 在 PATH 里（新开一个终端窗口测）。

### 3. Python 依赖

建议先建虚拟环境，避免污染全局：

```bash
python -m venv .venv
# Windows PowerShell
.venv\Scripts\Activate.ps1
# macOS / Linux
source .venv/bin/activate
```

然后装依赖。第三步要跑测试，所以装带测试依赖的那份：

```bash
pip install -r requirements-dev.txt
```

只想运行、不跑测试的话用 `pip install -r requirements.txt`，
运行时只需 `requests` 与 `python-dateutil` 两个包。

## 二、配 GitHub token

工具需要 token 调 GitHub API。两种方式，任选其一。

### 方式 A：gh CLI（推荐）

```bash
gh auth login
```

交互式登录，跟着提示选 GitHub.com → HTTPS → 浏览器授权。
登录后工具会自动调 `gh auth token` 取凭据，你不用再管。

装 gh：https://cli.github.com/

### 方式 B：环境变量

去 https://github.com/settings/tokens 生成一个 classic token，
勾选 `public_repo`（只读公开仓库够了；若组织有私有仓库需 `repo`）。

```bash
# Windows PowerShell（仅当前会话）
$env:GITHUB_TOKEN = "ghp_xxxx"

# macOS / Linux
export GITHUB_TOKEN=ghp_xxxx
```

工具查找顺序是 `GITHUB_TOKEN` → `GH_TOKEN` → `gh auth token`。

不要把 token 写进项目文件里提交。

### 验证 token 可用

```bash
python -c "from contributors.auth import get_token; t=get_token(); print('ok, 长度', len(t))"
```

打印 `ok, 长度 xx` 即可。报 `认证失败` 就回头检查上一步。

## 三、先跑测试确认环境正常

```bash
python -m pytest -q
```

期望 `299 passed`。这一步不联网、不消耗额度，几十秒完成。

Windows 上若终端输出中文乱码：

```bash
PYTHONIOENCODING=utf-8 python -m pytest -q
```

乱码只影响终端显示，写进文件的内容是正常的。

测试没全绿就先别往下跑 —— 环境有问题，全量跑出来的数字不可信。

## 四、先小范围试跑

不要一上来就跑全量。先拿一个小仓库验证整条链路：

```bash
python -m contributors --repos dpdata --months 3
```

约 1 分钟。看到类似输出即成功：

```
共 67 个仓库，跳过 66 个，待处理 1 个
[1/1] dpdata ...
统计区间: 2026-04-30 ~ 2026-07-31（UTC，含两端）
贡献者 XX 人，输出目录 output
```

然后翻一下 `output/` 里的文件，确认 `summary.csv` 有内容、
`run_meta.json` 的 `failures` 是空的。

## 五、跑全量

确认小范围没问题后：

```bash
python -m contributors --since 2026-01-01 --include-forks self --out-dir output_all
```

首次运行 10–20 分钟，主要在克隆。中途可以 Ctrl-C，已完成仓库的缓存会保留，
下次接着跑。

参数说明：

- `--since 2026-01-01`：统计起点。不给则默认一年前。
- `--include-forks self`：只纳入生态内部的 fork。这是当前确认过的口径，
  见 `README.md` 顶部的适用范围说明。
- `--out-dir output_all`：输出到单独目录，避免覆盖试跑结果。

跑完先看 `output_all/run_meta.json`：

- `failures` 应为 `{}`。非空说明有仓库处理失败，里面有原因。
- `skipped` 列出被跳过的仓库及原因，逐条看一遍确认没有意外跳过。
- `contributors` 是最终人数。
- `unmatched_emails` 是未能关联 GitHub 账号的身份数，需人工确认，
  明细在 `unmatched.csv`。

## 六、首次运行会遇到的几件事

### 磁盘预检把你挡住了

报「磁盘空间不足：预计需要 20000 MB，可用 xxx MB」。

这个估算是按 GitHub 报告的仓库体积算的，而实际克隆走
`--filter=blob:none` 不下载文件内容，真实需求小一到两个数量级
（实测全量约 550 MB，而预检会算出约 20 GB）。这是已知缺陷，
见 `README.md` 的「已知问题」。

绕法：分批跑，用 `--repos` 指定几个仓库跑一轮，缓存建立后预检就不再
把它们算进去。或用 `--cache-dir` 指到空间充足的盘。

### 克隆很慢或卡住

单仓库超时是 30 分钟。网络差的话建议先配 git 代理，或先跑
`--repos` 挑几个仓库分批建缓存。

### Windows 上终端中文乱码

加 `PYTHONIOENCODING=utf-8` 前缀。文件内容不受影响。

### 写 CSV 报 PermissionError

Excel 打开着输出文件会锁住它。关掉 Excel 窗口，或用 `--out-dir`
换个目录。

### 提示「N 个身份未能关联 GitHub 账号」

正常现象，不是错误。这些人提交时用的邮箱查不到对应 GitHub 账号
（域名拼错、未验证的私人邮箱、git 未配置身份等）。他们不会被丢弃，
在 `unmatched.csv` 里按提交数降序列出，附姓名和所在仓库，供人工确认。

## 七、之后再跑

缓存建立后就快了：

```bash
# 隔天重跑，只做增量 fetch，十几秒
python -m contributors --since 2026-01-01 --include-forks self --out-dir output_all

# 只改时间窗重算 commit 口径，零网络，秒级
python -m contributors --since 2026-03-01 --no-fetch --out-dir output_test
```

`--no-fetch` 完全跳过 GitHub API，PR/Issue 各列全为 0，且能关联账号的
比例大幅下降（实测 236 人掉到 175 人）。只适合快速验证 commit 口径，
出正式名单必须走完整跑法。

## 八、拿到结果后先看哪两列

提交数有两列，`commits` 和 `commits_loose`，每个人两列都有值。

- `commits` 只数合并进主干（分支与标签）的提交。
- `commits_loose` 额外计入 PR 分支上主干不可达的提交，恒 ≥ `commits`。

两列都不是「正确答案」，各有一处已知偏差：宽松口径在 squash 合并的仓库里
含重复计数（同一份工作在 PR 分支和主干各有一条记录，SHA 不同）；严格口径会
漏掉署名邮箱与 GitHub 账号对不上的人。

实测差距不小：全组织窗口内严格 6314 条、宽松 13856 条，独立邮箱 176 对 329。
所以别只看一列。

排名用 `commits`，找漏掉的人看两列差值大的行 —— 差值大通常意味着这个人的
PR 分支邮箱没被关联上，值得人工确认。完整说明见 `README.md` 的
「提交数的两个口径」。

身份归并部分（邮箱聚合、bot 判定、AI 助手识别）经核对可靠。
